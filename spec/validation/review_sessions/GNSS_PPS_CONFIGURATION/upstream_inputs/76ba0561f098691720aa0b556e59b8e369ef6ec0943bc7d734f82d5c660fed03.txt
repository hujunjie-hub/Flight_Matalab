# 产品配置、插件与参数管理（V1.9.1）

> **规范性：** 本文件是 Product Profile、产品能力、参数目录、配置Hash和CORE重编译/非安全设置事务策略的唯一来源。


> **文档编号：** 08  
> **范围：** Product Profile、编译期feature、车辆变体、构建配置、参数目录和调参规则。  
> **归并原则：** 保留原设计内容、接口定义、代码示例、约束和验收条款；本轮补齐类型、持久化和产品门控，改动与验证范围见12。

> **项目接入：** 目录的唯一定义见03 §0。产品/配置/插件是 `applications/` 下的后续扩展，第三方公用库归 `packages/`。当前仅有基础应用入口，下列 YAML、解析器、生成头和工具尚未创建；通过根 SCons/Kconfig 链接入，不为规格适配建立第二套工程。

## 1. 工程构建与调参管理

### 1. 产品组合与工程调参分离

每个固件/Host 目标只能选择一个 `PRODUCT_PROFILE`。Product Manifest 选择车辆契约、平台、插件、硬件、接口 layout 和编译期结构；`applications/config/<PRODUCT>/` 只提供该产品的少量工程调参值。

```text
applications/                         # 统一应用根；以下子目录为规划
  contracts/                          # 唯一 ICD/Product Contract selector
  core/m1/ ... core/m7/                # 唯一公共核心
  services/health/                    # HEALTH + Sensor Integrity Manager
  platform/rtthread53/                 # 到现有 RTOS/设备的薄适配
  plugins/                            # 项目自有 Port/策略适配
  products/QUAD_X4_H723/               # 产品/硬件/插件 manifest
  config/QUAD_X4/                      # 四份工程调参文件
  calibration/                        # 原始标定证据和报告
  sim/plant/、sim/sensors/             # Host/SIL/HIL only
packages/<package>/                   # 第三方公用源码，复用现有包入口
build/generated/                      # 应用生成配置，不手工编辑
```

### 2. 编译期绑定

使用 C-compatible Port 和强类型 Product Contract；直接静态链接。每个 Port 恰好一个实现；缺失/重复实现链接失败。禁止动态库、运行时插件扫描、反射、RTTI、运行时车辆切换。公共核心不 include 车辆私有头、HAL、RTOS 私有或 Simulink 生成代码。

### 3. 工程调参文件边界

QUAD_X4 只保留四份：`vehicle_model.yaml`、`sensor_alignment.yaml`、`estimator_tuning.yaml`、`controller_tuning.yaml`。它们分别用于物理模型、安装外参、导航噪声模型和闭环控制整定。

硬件 BOM/ODR/协议/插件选择进入 Product Manifest；FMS/FDIR/通信安全策略由车辆专用策略代码和受控安全契约管理；MPC 采样周期/Np/Nc 记录在 controller_tuning.yaml 的 mpc_structure 但仅编译期生效；缓冲区容量、任务周期、求解器迭代上限和状态维数属于平台/实现结构。不得把所有数字无差别搬进 YAML。

### 4. 配置生成

- 后续实现 `applications/tools/config_validate.py` 并接入 SCons 依赖，在 PC/构建期检查四份 YAML 的结构、单位约定、数值有效性和产品一致性。
- H723 不运行 YAML parser；构建生成静态只读 C 结构，进入固件 `.rodata`。
- 必填 `null/TBD`、Profile 不兼容、四元数未归一、惯量矩阵明显非法和跨文件冲突必须阻止 Release 构建。
- 生成物位于 `build/generated/`，不手工编辑；构建应可重复。
- `applications/calibration/` 保存原始报告和数据集；最终有效杆臂/安装外参只有 `sensor_alignment.yaml` 一个运行时来源。

### 5. 参数生效纪律

四份工程调参只在Host修改、校验并重编译固件后生效；地面维护可安装新固件，但不直接把Flash新槽覆盖核心参数。飞行中禁止更新这些核心调参。每次变更记录参数集 hash、模型/数据集 hash、固件 commit、测试指标和回滚版本。

安全包线、RC/数传失联、接管、RTL、FDIR 隔离/恢复行为不是普通调参；修改必须走 CR、Agent D 独立审查和用户批准。

### 6. RT-Thread

复用本地 `rt-thread/`、`board/`、`libraries/HAL_Drivers/` 与现有 `packages/`，按RT-Thread v5.3.0设计基线核对实际来源；后续锁完整commit/内容Hash、补丁、编译器和SCons/Env，不重新导入/生成BSP或驱动。驱动直接使用原生Device Framework、原生bus/device/IPC/timer/DMA机制；RT-Thread原生Device Framework是唯一设备注册/生命周期框架，不创建第二套DeviceInstance/DriverManager/DriverOps。

### 7. CI 构建门禁

- Port 零/多实现负向构建。
- Product Manifest 兼容矩阵和 ABI/layout hash。
- 四份工程调参文件结构、单位、范围、必填值和 hash 检查。
- 参数生成可重复性和 manifest/hash。
- 公共核心依赖扫描、车辆私有 include 扫描、RTOS/HAL 边界扫描。
- 静态分析、单测、SIL、故障注入、HIL、资源预算和安全审查。
- 安全策略 CR 与普通工程调参变更必须使用不同审批路径。

### GNSS主要器件的固定Feature与运行期质量规则

QUAD_X4_H723固定安装UM982：Product Manifest必须声明GNSS required=true、enabled=true、pps_capture=true；对应GNSS_SUPPORT=1和GNSS_PPS_CAPTURE=1。BSP强制接入UART4 RX DMA、TIM2_CH3及其IRQ/缓冲，不提供默认关闭或无GNSS硬件生产Profile。禁用任一必需配置必须由配置/编译检查拒绝。

运动中无Fix、PVT过期、串口/PPS/UTC中断及恢复是运行期质量/故障状态，不修改这些编译期字段，也不拆除驱动或源健康对象。CI验证标准必装产品和运行期丢失/恢复故障注入；本地monotonic/IMU不等待外部信号。协议解析未完成与观测未通过验证必须独立标NOT_READY/未验收，不得通过GNSS_SUPPORT=0替代实现。RTC及其他外部同步源仍按实际硬件配置。

## 2. Product Profile 与编译期插件组合规范

### 1. 单一组合根

每个可执行目标必须且只能选择一个 `PRODUCT_PROFILE`。Profile 是组合根，不允许通过多个彼此独立、无约束的宏任意拼装产品。

示例：`QUAD_X4_H723`、`UGV_BICYCLE_HOST`、`USV_3DOF_HOST`。首版以QUAD_X4_H723为实现目标，实际生产验证仍待执行。

### 2. Profile Manifest 字段

- product/profile ID/version/hash。
- vehicle contract ID、vehicle class、canonical frames。
- platform/BSP/RTOS ID。
- selected FMS Policy、Estimator、Guidance、Controller Pipeline。
- selected Control Model、Actuator Layout/Adapter、sensor set。
- NavState/MotionReference/ActuatorDemand typed layout IDs。
- supported operation/capability set。
- model/parameter hashes、static memory budget、task period set。
- Host-only Plant/Sensor Simulation Model IDs（实机固件中为 NONE）。

### 3. 兼容矩阵

构建系统必须检查 FMS/Estimator/Guidance/Controller/ControlModel/Actuator/Platform 之间的兼容性：vehicle contract、frame、state layout、motion reference layout、control layout、actuator layout、采样周期、资源预算和支持能力。禁止出现跨车辆错误组合。开发者只能在 Profile allow-list 中选择算法替代项。

### 4. 插件清单

- `FmsPolicyPort`：完整 Aerial/Ground/Marine 操作策略。
- `EstimatorPort`：QUAD_X4首版绑定KF-GINS_QUAD（21维核心+1维Baro bias）；其他Profile可选择符合ICD的UKF等完整导航估计器。
- `GuidancePort`：车辆专用任务/路径/运动参考生成。
- `ControllerPort`：车辆专用完整闭环控制 pipeline。
- `ControlModelPort`：MPC/LQR 预测模型，可与 Controller 独立替换但需兼容检查。
- `ActuatorPort`：车辆/执行器布局专用物理需求到原生设备输出适配。
- `Host/SIL/HIL专用PlantSimulationPort（仅Host/SIL/HIL）`/`SensorSimulationPort`：Host/SIL/HIL only。

Estimator Motion Model 默认内部归 Estimator；Actuator Effectiveness Data 归 M6；Actuator Calibration Map 归 M7；Actuator Dynamics 归 Plant Simulation Model。

### 5. 编译期绑定

C-compatible Port 函数由选中的实现提供同名符号，直接静态链接。每个 Port 恰好一个实现；缺失或重复必须构建/链接失败。没有动态加载、运行时扫描、反射或车辆热切换。算法内部可以使用 C++，但跨模块 ABI 使用固定宽度 C 类型和强类型 Product Contract。

### 6. 目录原则

允许按插件实现分组源文件，但不复制 M1-M7 公共目录：

```text
applications/core/m1/ ... applications/core/m7/ # 唯一公共核心
applications/contracts/                       # 公共 ICD + product selector
applications/plugins/                         # 按 fms/estimator/guidance 等实现分组
applications/platform/rtthread53/             # 仅薄适配，底层驱动保持原位
applications/products/<profile>/              # manifest/产品契约/绑定
applications/sim/                             # Host-only 仿真
packages/<package>/                           # 算法/协议/器件通用源码
```

### 7. 替换验收

替换任一 FMS/Estimator/Guidance/Controller/ControlModel/Actuator/Plant 实现时：公共消费者源代码不变；只允许更换 Profile 绑定和实现；ABI/契约测试通过；数值/实时/安全测试重新执行。替换成功不自动代表该车辆或算法获得实物安全认证。

### 必装GNSS与独立本地时钟

UM982及其UART4/PPS接口是当前Flight主要器件的固定接入。GNSS信号可在运动中丢失，平台保留本地monotonic/IMU采集和原接收通道，以TimeServiceStatus、SensorHealth和NavigationCapability发布真实质量；仅对无效观测拒绝融合。RTC和其他同步源是否安装仍由实际BOM决定。其他车辆的硬件需求另立产品合同，不改变本Flight基线。

## 3. 工程调参边界与参数管理规范

### 1. 设计目标

`applications/config/` 服务于工程师调试模型和优化闭环性能，不是全系统“万能参数仓库”。本项目只集中管理四类真正需要工程师辨识或反复整定的参数：

1. 被控对象物理模型；
2. 传感器安装外参与时间偏差；
3. 组合导航噪声模型和初始不确定度；
4. 控制器增益与优化权重。

其他参数继续由其所属机制管理。不要为了消除硬编码而把每个常量、每个超时、每个状态机分支都变成 YAML 字段。**配置化的判断标准是“是否需要工程师基于数据反复调整”，不是“它是不是一个数字”。**

### 2. 唯一精简目录

```text
applications/config/
├── README.md
└── QUAD_X4/
    ├── vehicle_model.yaml
    ├── sensor_alignment.yaml
    ├── estimator_tuning.yaml
    └── controller_tuning.yaml

applications/products/QUAD_X4_H723/
└── product_manifest.yaml

applications/calibration/
└── README.md                 # 原始标定证据、报告和数据集归档
```

未来增加 UGV/USV 时，按同一工程语义增加对应 profile 文件组；不复制 M1～M7 业务代码，也不为每个软件模块新建一层配置目录。首版CORE调参只维护QUAD_X4四个源文件；运行时非安全设置不是第五份算法调参YAML。

### 3. 四类工程调参的边界

| 文件 | 放什么 | 典型例子 | Owner |
|---|---|---|---|
| `vehicle_model.yaml` | 被控对象可辨识物理参数 | 质量、重心、惯量、旋翼位置/旋向、推力曲线、电机时间常数、必要时的气动阻力参数 | Agent C |
| `sensor_alignment.yaml` | 传感器到车体的几何/时间外参 | IMU/GNSS/磁力计/气压计/测距仪安装旋转、杆臂、剩余时间偏差、区域磁偏角/磁场参考模型 | Agent B（Agent A 提供硬件测量事实） |
| `estimator_tuning.yaml` | KF-GINS_QUAD随机噪声和初始不确定度 | 陀螺ARW/加速度VRW、bias/scale先验与相关时间、22维完整初始协方差（21维核心+Baro bias及必要交叉项）、Baro bias先验/随机游走、GNSS位置/速度噪声floor、Baro噪声floor、Mag航向噪声与启用策略 | Agent B |
| `controller_tuning.yaml` | 控制器整定与结构参数 | SO(3) 增益、Rate PID、MPC Q/R 权重、Np/Nc/采样周期（仅编译期生效）、备用位置/速度控制增益 | Agent C |

参数必须具有明确单位、来源、适用产品、版本和辨识/整定记录。每个参数只允许一个权威值；不得在 C 代码、Simulink Model Workspace 和 YAML 中各保存一份互相独立的数值。

### 3.1 QUAD_X4 KF-GINS参数分层（规范性）

- `sensor_alignment.yaml`唯一保存IMU安装旋转、IMU-GNSS天线杆臂（方向定义IMU测量中心→天线相位中心）、IMU-Mag旋转、Baro安装位置、区域磁偏角/磁场参考模型及经辨识的sample-time/group-delay修正。
- `estimator_tuning.yaml`保存KF-GINS噪声谱密度、bias/scale先验、初始协方差、GNSS位置/速度与Baro/Mag观测噪声模型。
- 21/22维状态排列、双子样算法、观测方程、NIS统计门限、history长度、replay分片、矩阵精度和WCET预算不是运行时调参项；修改必须走代码CR和完整回归。
- 首版GNSS position/velocity、Baro height、Mag heading分别由Profile声明；Mag运行中融合可关闭，不能仅因BMM350安装就默认始终信任。
- 固件不解析YAML；Host校验器在构建期生成固定维数、静态只读C/C++配置。

#### 3.2 围栏编译期配置入口（CR-V191-C02，规范性）

- 首版围栏唯一来源是 `applications/products/QUAD_X4_H723/product_manifest.yaml` 的 `geofence`
  段（或等价受控Product Profile输入），Host校验后生成只读`ProductGeofenceConfig`到`.rodata`；
  不新增运行时`SET_GEOFENCE`命令，也不进入普通`controller_tuning.yaml`/参数事务。
- `ProductGeofenceConfig`包含`profile_hash`、`config_version`、`geofence_hash`和最多
  `PRODUCT_MAX_GEOFENCE_POLYGONS`个`ProductGeofenceDefinition`；Composition Root在
  `fms_policy_init`前通过产品专用安装钩子
  `quad_x4_fms_configure_product_geofence(const ProductGeofenceConfig*)`安装（非公共Port，
  运行时不重装）；M4在`fms_policy_init`校验上述hash与frame=NED、顶点数、几何、高度上下界、
  margin后才持有并发布`ProductGeofenceSnapshot`。
- `geofence_hash`必须进入Product Profile hash；任何围栏变更都是安全契约变更，必须走CR、重编译
  并重跑围栏/任务测试。Companion只能提交任务/路径候选，不能修改围栏；运行时无围栏写接口。
- 围栏无效/过期/Origin或state_epoch不匹配时，依赖围栏的任务和模式拒绝启动；测试见09
  `TEST-V191-GEOFENCE`，目标/HIL证据仍为NOT_RUN。

### 4. 明确不进入日常调参集的参数

| 参数类型 | 所属位置 | 原因 |
|---|---|---|
| MCU/板卡/传感器型号、总线、ODR、FIFO、ESC 协议、通道映射 | Product Manifest、BSP、原生 RT-Thread 驱动 | 硬件事实，不是控制调参 |
| FMS 模式状态机、RC/数传失联动作、接管锁存、RTL/降落策略、能源和地理围栏安全门限 | 车辆专用 FMS Policy 与受控安全契约；围栏几何/高度/margin见§3.2编译期`ProductGeofenceConfig` | 安全策略，修改必须走 CR/独立审查，不应成为普通调参旋钮；运行时无围栏写接口 |
| 传感器源级隔离/恢复策略、FDIR 状态机和统计门控规则 | Sensor Integrity 实现及安全规范 | 不能因调参方便而随意改变安全行为；单次 NIS 异常仍不得永久隔离 |
| 任务/轨迹速度限制、最大倾角、加速度/推力安全包线 | 车辆能力与 FMS SafetyEnvelope | 属于运行安全边界，不等于控制器权重/增益 |
| 状态维数、求解器迭代上限、DMA ring 容量、RTOS 周期/栈 | Product Manifest、Kconfig、实现常量 | 影响内存布局和实时性，改变后必须重编译并重新验收；MPC 采样周期/Np/Nc 统一记录在 controller_tuning.yaml 的 mpc_structure 中，但仅编译期生效 |
| 统计卡方门限、协议常量、数值稳定 epsilon 等内部常量 | 算法/协议实现 | 有数学或协议依据，不应让调参人员随意修改 |
| 传感器原始标定日志、Allan 方差报告、推力台架报告 | `applications/calibration/` | 保存证据，不作为第二份运行时参数源 |

如某个安全策略参数确实需要因特定接收机、ESC 或车辆差异而变化，应通过产品安全契约和 CR 管理，不得偷偷塞入普通 `controller_tuning.yaml`。

### 5. 防止参数膨胀和重复

- 只保存原始独立参数；可推导值不重复保存。例如预测时长由 `Np × Ts` 得到，不再同时维护一个可独立修改的 horizon_seconds。`mpc_structure` 中的 Ts/Np/Nc 只在编译期读取，不能在飞行中热更新。
- MPC 权重保留工程上有意义的分组（XY/Z、位置/速度/控制量/控制变化），不暴露每个矩阵元素。
- PID 按 Roll/Pitch 共用、Yaw 独立组织，不给每个轴无必要地复制整套参数。
- 物理推力曲线只维护一份；M7 逆映射和 Host Plant 使用同一数据来源/生成结果，不得各自手工拟合。
- 传感器杆臂/安装旋转只在 `sensor_alignment.yaml` 保存一次；M2/M3 通过只读配置接口获取，不得在各自模块另存副本。
- NIS/innovation 统计门限按自由度和固定置信策略在算法内部计算；噪声模型调整通过 estimator tuning 完成，禁止为了“让数据通过”任意放宽门限。
- 任何参数若连续多个版本从未被工程师调整、且没有产品差异价值，应评估是否移回实现常量。

### 6. Product Manifest、标定和调参的区别

- `applications/products/<PRODUCT>/product_manifest.yaml`：回答“这台产品由什么硬件、哪组插件和哪些编译期维数组成”。
- `applications/config/<PRODUCT>/`：回答“这个已确定产品的模型、导航和控制性能参数是多少”。
- `applications/calibration/`：回答“这些参数如何测得，证据和数据集是什么”。

三者不能互相替代。H723 不解析 YAML；构建期校验后生成静态只读 C 配置。运行时不要求文件系统，也不在高频任务解析配置。

### 7. 工程调参顺序

1. **确认硬件事实**：传感器型号/ODR/时间源、安装位置、ESC/电机/桨叶和板卡版本先冻结。
2. **传感器安装对齐**：先校准坐标旋转、杆臂和时间偏差；确认 frame、符号和参考点。杆臂错误不能用滤波噪声或 PID 掩盖。
3. **被控对象辨识**：称重、重心、惯量估计、推力台架和电机响应辨识；先让 Plant/Control Model 有可信物理基础。
4. **组合导航整定**：用静态/动态数据估计 IMU 噪声和观测噪声，再检查延迟、残差和跨源一致性。
5. **控制器整定**：先 Rate PID，再 SO(3)，最后平动 MPC；MPC 权重不能代替错误的质量/惯量/推力模型。
6. **验证**：PC 回放/SIL → PIL → HIL → 无桨台架 → 受控实物测试。每一步记录同一参数集 hash。
7. 一次只改一个参数组；每次保存 baseline、修改理由、数据集、前后指标和回滚版本。

### 8. 工程师调参记录模板

每次试验只需要记录以下信息，不要求维护庞大的参数数据库：

| 项目 | 记录内容 |
|---|---|
| 基线 | Product ID、固件 commit、四份调参文件 revision/hash |
| 对象 | vehicle model / sensor alignment / estimator / controller（一次选一个主对象） |
| 变更 | 参数名、旧值、新值、单位、修改理由 |
| 数据 | 原始日志/数据集 ID 与 SHA256、测试场景、载荷/电压/环境 |
| 指标 | 导航误差、姿态/角速度跟踪、超调/稳态误差、控制输出余量、CPU/WCET（按本次目标选择） |
| 结论 | 接受/回滚/继续试验、审核人和日期 |

不要为了每次调参再创建一份新的 YAML。调参历史放版本控制提交记录和试验报告，当前生效值只留在四份文件中。

### 9. 生效、回滚和追溯

#### 9.1 两类配置的权威来源与生效（唯一规则）

| 类别 | 唯一生效来源 | 修改/回滚 | Hash/兼容性 |
|---|---|---|---|
| CORE：四份vehicle_model/sensor_alignment/estimator_tuning/controller_tuning | 构建生成、固件.rodata，只读 | 只在Host改源文件并重编译；地面维护安装/回滚完整固件 | core_parameter_hash与Firmware manifest精确匹配 |
| NONSAFETY_SETTINGS：下列明确白名单 | W25Q64完整提交且兼容的A/B journal；不存在有效槽时用固件内置默认值 | DISARMED+维护授权下唯一Parameter Manager事务 | settings_schema/profile_id/settings_hash独立于core_parameter_hash |
| 原始标定、SD镜像、旧固件参数导出 | 证据/备份，不能直接成为生效来源 | 人工审核后只回填四份源文件再构建 | 数据集/报告SHA256用于追溯 |

CORE包括MPC Ts/Np/Nc、噪声/初始P、安装外参、模型/增益/推力映射；FMS/FDIR安全策略由受控代码/Profile管理，也不能通过普通参数事务覆盖。核心Hash不符拒绝进入READY/ARMED；不尝试从Flash“修复”核心值。地面修改导航噪声同样必须重编译，不能因DISARMED而绕过。

非安全白名单首版仅两项：LOG_DETAIL_LEVEL（整数0..3，默认1，只影响非关键日志）；TELEM_DEBUG_DIV（整数1..8，默认1，只影响P3调试遥测降采样）。两项不得改变P0 ACK/安全事件、heartbeat、采样/控制频率或存储安全保留槽。任何新增参数必须登记单位/范围/权限/生效点和兼容版本；未知字段拒绝，不能自由写内存。

NonSafetySettings事务唯一为PREPARE→SCHEMA/RANGE/PROFILE_VALIDATE→WRITE_INACTIVE_SLOT→READBACK_VERIFY→COMMIT→ACTIVATE_WHEN_DISARMED→HEALTH_CONFIRM。每槽≤64KiB；header/payload/CRC32C/commit metadata和对齐都包含在槽内。commit marker最后写；未提交/未健康确认/CRC错槽不参与启动选择。两个64KiB槽总128KiB，布局见07；旧槽在新槽健康确认前保留。

启动选择：先验证固件CORE/ABI/Profile；再选generation最高、完整提交且HEALTH_CONFIRMED、settings_schema与profile_id受当前固件支持的槽。没有有效槽或激活失败，保持上个兼容settings视图；无上个视图则使用编译默认值并报告设置恢复事件。非安全设置坏不能掩盖CORE错误，也不应凭空宣布核心参数失效。SD镜像从不自动回灌。

运行时采用固定双缓冲只读settings视图，Parameter Manager在DISARMED维护点原子切换；CriticalFlashTask是W25Q64写入唯一执行者。除DISARMED外PREPARE/COMMIT/ACTIVATE/CONFIRM均拒绝，包括ARMING/DISARMING。维护事务持有maintenance_epoch租约，M4在租约有效时拒绝Arm；状态变化撤销租约并放弃未确认候选。每次变更记录settings_hash、core_parameter_hash、profile_hash、固件commit和事务generation，三者不得混成一个可手填hash。实际Flash掉电/寿命/几何验证仍NOT_RUN。

### 10. 验收要求

- 只有四个调参文件；不再出现按 M1～M7、FMS、FDIR、通信、平台等模块无限拆分的配置目录。
- 所有运行时有效调参值均能追溯到唯一文件/唯一 revision。
- Simulink、SIL、HIL 和 H723 使用同一参数集和 hash；禁止隐藏参数副本。
- 待规划工具实际交付后，从工程根执行 `python applications/tools/config_validate.py`，通过模板结构检查；`--release` 在必填值未辨识时必须失败。
- 参数修改后执行相应回归测试；改变编译期结构或安全策略时执行完整专项评审。

### 11. 首版未决项

质量/惯量/重心、旋翼几何、推力曲线、电机时间常数、传感器杆臂/安装角/时间偏差、IMU Allan 数据、各观测噪声、SO(3)/PID/MPC 权重均须由实际硬件和数据集确定。本规范不伪造默认数值。

## 4. QUAD_X4_H723 Product Profile 与参数生效规范

### 1. Flight.xlsx硬件配置清单输入

- MCU：STM32H723ZGT6（Flight.xlsx清单）；时钟、TIM和外设频率按Flight.xlsx记录作为核对基准，最终以真实`.ioc`和生成代码为准。
- IMU：ADIS16505-2。
- RC：USART3 / 115200 baud；Flight.xlsx与05已统一名称ELRS，实物型号/串口协议待核实。
- GCS数传：USART2 / MAVLink 2 / 115200 baud。
- ESC：DShot300或DShot600，作为Profile编译期协议选择；Flight.xlsx记录TIM1_UP→DMA2_Stream2、CH1–4共享DMA Burst。软件在输出运行前按Profile配置TIM1高频bit-time时基，TIM2_CH1独立调度400Hz帧刷新；CNDTR=68、active零/preload bit0、bit1–15及两个zero-tail、绝对raw截止收尾的布局按07 §3.0.1唯一软件基线实现；上机阶段验收波形。
- W25Q64：通用8MiB逻辑分区；SD：先实现基础MBR/FAT32异步日志。
- Companion：临时USART1/MAVLink2/115200，占位且与Debug/FinSH互斥。
- Hardware Kill：本轮不作为软件实现阻塞；不得宣称板上已具备物理Kill/BKIN。
- 在线避障：Host/SIL完成SIMULATION/STATIC_MAP软件闭环；真实飞行QUAD Profile固定`OBSTACLE_SOURCE_MODE=NONE`。传感器适配后续单独启用/验收。

### 2. 通用四旋翼模型

第一版采用参数化X型四旋翼ControlModel/Plant。`vehicle_model.yaml`包含质量、重心、惯量矩阵、臂长、电机编号/位置/旋向、推力/反扭矩系数、电机动态和推力上下限。当前没有实机测量值的字段统一标记`SIM_ONLY`，只用于Host/SIL；不得被实机放行Profile继承。实机电机编号/旋向必须在上机阶段逐路核对。

### 3. ESC与Companion编译期Profile

`ESC_PROTOCOL`只允许`DSHOT300`或`DSHOT600`。协议bit rate与控制环频率、帧刷新频率分别配置；Flight.xlsx记录的TIM1_UP→DMA2_Stream2仅是配置清单，芯片静态路由已确认`DMA_REQUEST_TIM1_UP=15U`→DMAMUX1_Channel10→DMA2_Stream2；实际项目配置和TIM1更新时序仍须来自受控`.ioc`/生成代码，不在YAML中自由改写。Flight.xlsx的TIM1 PSC=274、ARR=2499、kernel=275MHz对应1MHz计数时钟和400Hz默认周期；该默认配置不直接用于DShot位编码。DShot使能时由平台驱动按07 §3.0.1运行期配置高频bit-time时基，CNDTR/CCR preload和双zero-tail结束策略已形成软件基线；目标波形证据单独记录为`verification_status=NOT_RUN`，不表示设计未定义。QUAD首版固定`ESC_FEEDBACK_CAPABILITY=NONE`；未完成双向DShot/ESC telemetry硬件、协议和目标测试前，不允许将其改为可用，也不得宣称具备RPM/单电机失速直接反馈。

`COMPANION_TRANSPORT=USART1`为临时Profile；`DEBUG_UART1=1`与`COMPANION_TRANSPORT=USART1`互斥，构建校验必须拒绝两者同时启用。更换物理UART时只改平台资源映射，不改变Companion消息契约。

### 4. 障碍能力门控

NONE允许不要求避障的普通任务，发布OBSTACLE_ASSURANCE_UNAVAILABLE；要求避障任务拒绝。动力学、时间/epoch、当前项token、参考连续性及适用围栏始终验证。STATIC_MAP/SIMULATION/ONBOARD_SENSOR依赖障碍时未知空间fail-closed，不能在失联后无声改为NONE。详细矩阵唯一见04第7节。

Host/SIL可选`SIMULATION`或`STATIC_MAP`；真实QUAD飞行Profile固定`NONE`。未知空间不是自由空间。未接入并验收真实障碍传感器前，不开放在线动态避障飞行模式；软件框架完成后该功能在真实飞行Profile保持关闭。

### 5. 参数和版本纪律

控制器的Rate PID增益以物理力矩输出单位定义；历史归一化输出域增益不得直接复用。MPC结构参数`Ts/Np/Nc`为编译期结构值；权重和控制增益在SIL中起始整定，Profile hash必须包含配置版本。所有SIM_ONLY参数不得被Release配置解析器静默转换成实机参数。

### 12. 首版序列化、持久化和缺省行为

NONSAFETY_SETTINGS槽内首条记录为64B little-endian：offset0 magic=0x46535447(u32)，4 wire_schema=1(u16)，6 length=64(u16)，8 profile_id(u32)，12 generation(u32，1起不回绕)，16 payload_length=8(u32)，20 payload_crc32c(u32)，24 header_crc32c(u32，覆盖0..23)，28 reserved=0(u32)，32 LOG_DETAIL_LEVEL(u32)，36 TELEM_DEBUG_DIV(u32)，40 commit=0x434F4D4D(u32)，44 confirmed=0x4845414C(u32)，48..63保留0xFF。擦除态全FF；写header/payload→回读CRC→最后编程commit→DISARMED内存激活/健康检查→最后编程confirmed。旧confirmed槽在新confirmed写成前不擦除；任何掉电只选择confirmed且CRC/范围/兼容校验成功的最高generation，不能把仅commit的试用值当已确认。CONFIRM失败回旧视图/默认并记录故障。更新每槽先擦除，不能覆写非擦除generation；达到UINT32_MAX拒绝新事务并维护换代。

CRC32C：反射多项式0x82F63B78，init/xorout均0xFFFFFFFF，输入ASCII `123456789`结果0xE3069283。CRC只检测损坏，不代替认证。Header里的32bit hash仅诊断指纹；发布/配置证据以完整SHA256为准。CORE生成Hash覆盖四份源文件和manifest的规范化内容：UTF-8/LF、键字典序、禁止重复键/NaN/Inf/隐式单位，数值解析成带单位schema后按固定宽度LE字段顺序序列化，字段schema及生成器版本一同入Hash；不对包含hash字段的自身循环求hash。未实现生成器前不接受手填hash作为发布证据。

首版H723 `OUTPUT_POLICY=BENCH_INHIBIT(1)`、`BOOT_MODE=DIRECT_BSP`、`OBSTACLE_SOURCE_MODE=NONE`、`ESC_FEEDBACK_CAPABILITY=NONE`。BENCH_INHIBIT禁止使能电机物理输出，允许传感器/导航/软件状态集成；Host/SIL使用独立`SIM_ONLY`参数和`SIM_CONTROLLED_STOP(2)`。真实飞行policy必须登记>=0x100的唯一ID并完成下述证据，不能用通用零输出代替空中安全动作。RC协议/电池电流模型/接地证据/电机与推力参数/安装和时延标定尚缺时，对应能力标记UNAVAILABLE；解锁门控拒绝依赖该能力的实际运动，不能继承SIM_ONLY常数。

所有五个Port config由02的完整固定宽度结构生成；版本/字节数/只读lifetime、有限值、正质量/SPD惯量与初始P、非负噪声/增益、推力单调映射、四电机置换、模式能力、资源allow-list逐项校验。缺必填字段或verified_policy_mask不满足Profile即validate失败。`struct_bytes`是当前target的sizeof，只在同ABI内部使用，持久化/网络不得直接memcpy该结构。

CORE到配置映射固定：vehicle_model→Controller质量/惯量/旋翼几何与Actuator thrust曲线；sensor_alignment→QuadSensorProcessingConfig及Estimator杆臂/磁偏角；estimator_tuning→Estimator噪声/初始P；controller_tuning→Controller增益/Q/R/S/延迟，重复derived值只由生成器计算。Product Manifest给初始已知地理锚点/来源、资源/模式/ODR，锚点不是可在线改写的调参；缺失时Estimator不能越过INITIALIZING。编译生成后各Port validate检查与Profile/hash完全匹配。

IMU→CG杆臂由vehicle_model中的IMU安装位置和CG位置唯一推导，生成给Estimator配置；sensor_alignment不再保存该杆臂的独立手填副本。IMU→GNSS天线杆臂仍按sensor_alignment权威值生成。
