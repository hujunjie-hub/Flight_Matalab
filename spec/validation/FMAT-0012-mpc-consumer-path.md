# FMAT-0012 附记：MPC 快照的消费路径

- 记录时间：第 30 轮
- 目的：为"MPC 合法解却有害"这一结论提供精确的下阶段入口
- 状态：路径已确认，根因未定

## 1. 唯一消费者

`middleware/model/control/outer_loop/quad_x4/position_tracking/position_control.c:61` 的 `position_control_track()`：

```c
mpc_read(&cached_mpc);                                   /* L74 */
backup = !(cached_mpc.expires_at_us > in->evaluation_time_us &&
           same_clock(&cached_mpc.header, &in->navigation->header) &&
           cached_mpc.state_epoch   == in->navigation->state_epoch &&
           cached_mpc.origin_id     == in->navigation->origin_id &&
           cached_mpc.reference_epoch == epoch &&
           cached_mpc.authority_epoch == in->authority_status->authority_epoch &&
           cached_mpc.directive_epoch == in->directive->directive_epoch &&
           cached_mpc.envelope_epoch  == in->safety_envelope->envelope_epoch &&
           cached_mpc.model_epoch     == in->control_model_view->model_epoch &&
           cached_mpc.safety_envelope_id == in->safety_envelope->safety_envelope_id);  /* L87-98 */
for (i = 0; i < 3; ++i)
  if (fabsf(nav.position - cached_mpc.position[i]) > 0.5f ||
      fabsf(nav.velocity - cached_mpc.velocity[i]) > 0.5f)
    backup = 1;                                          /* L100-105 */
requested[i] = backup ? ref.acc + kp*(ref.pos - nav.pos) + kd*(ref.vel - nav.vel)
                      : cached_mpc.acceleration[i];      /* L106-114 */
```

即：快照在**有效期、时钟、六类 epoch、包线 id 全部一致**且**导航相对快照种子偏离 ≤0.5 m / 0.5 m/s** 时，MPC 的 `acceleration` 被直接当作期望加速度；否则走 PD 回退。

## 2. 与实测现象的一致性

| 实验 | 求解被接受 | 结果 |
|---|---|---|
| 基线 | 20 / 488（4.1%） | 通过，2.098 m |
| 放宽候选门限 | 449 / 489（91.8%） | 起飞失败 |
| 收紧求解器容差（门限不变） | 468 / 489（95.7%） | 起飞失败 |

基线那 20 个解集中在悬停附近（偏离小、加速度小），MPC 实质不介入；一旦接受数上升，加速/爬升段的解就进入姿态环。消费路径与现象一致。

## 3. 待确认的语义

`mpc_solve()` 末尾 `memcpy(out->acceleration, x, 3*sizeof(float))` 取首个控制移动的前三个分量。从上下界 `lower/upper[135+index] = ±0.02*slew + (k==0 ? prev[i] : 0)` 判断，变量应为**绝对加速度**，`prev` 只约束首步斜率。

若该判断成立，"合法解却有害"只剩四种解释：

1. `response()` 的 20 ms 预测与实际闭环在量纲/符号上不一致（尤其 `move==4` 的常值段与 `velocity` 分支）；
2. 代价权重 `q=[8,8,12,3,3,4]`、`r=[0.8,0.8,1]`、`s=[0.2,0.2,0.25]` 与实际动力学、`actuation_preview_delay_s=0.002` 的时序不匹配；
3. `state_min/max = ±100 m` 相对约 1 m 的实际状态尺度失衡，约束活跃时给出偏置解；
4. 首步对应 `control_time + preview_delay`，而消费侧在 `evaluation_time` 直接使用，2 ms 相位差与 1 kHz 内环不匹配。

## 4. 建议做法

不要再用"提高成功率"来验证（已被三次实验否证）。建议在 `position_control_track()` 增加诊断通道，同时记录：

- `backup` 标志；
- `cached_mpc.acceleration`；
- PD 回退给出的 `requested`；

一次 MIL 即可看出爬升段两者差异的方向与量级，比继续猜代价参数高效。该诊断只在 Host 侧开启，不改变固件行为。

## 4.1 第 31 轮的实测（Host 只读诊断）

在 `position_control_track()` 增加 Host 专用诊断（`#ifdef FLIGHT_HOST_TEST`，只读、不改行为），26 s MIL 得到：

三点结论：

1. **MPC 在这 9.76 s 里只被采用 80 个 1 kHz 周期（约 80 ms）**，参与度极低；
2. 被采用时 MPC 与 PD 的差异最大仅 **0.16 m/s²**（约 1.6% g），幅度很小；
3. 快照有效期实测恒为 **8 ms**，而外环周期是 20 ms——即使求解成功，也只有约 40% 的时间窗可用。

第 3 点若成立，将直接解释"MPC 参与度低"；但也可能是我的测量口径问题：寿命用 `expires_at_us - header.timestamp_sample_us` 计算，而 `timestamp_sample_us` 的语义（导航采样时刻 vs 求解时刻）尚未核实。**该数字在核实前不应作为结论引用。**

诊断代码已回退（Host 与固件均恢复原状，MIL 短跑 `MIL_OK`），避免把未核实的口径留在固件里。若下一阶段继续，建议先把 `expires_at_us` 的 min 链逐项打印出来（本轮的索引记录返回 0，即 `start+20000`，与 8 ms 的实测矛盾，说明口径还需查清）。

## 4.2 第 36 轮：快照到期被执行器消息掐住（已核实）

在消费侧记录被采用那一刻的三个时间戳（Host 只读，26 s MIL）：

```json
{ "used_samples": 80,
  "expires_us": 13905000, "sample_us": 13897000, "eval_us": 13904000,
  "life_us": 8000, "expires_minus_eval_us": 1000 }
```

- `sample_us` 是导航采样时刻，`eval_us` 是消费时刻，两者相差 **7 ms**；
- 快照的 `expires_at_us = sample + 8000`，因此被消费时只剩 **1 ms**；
- 外环周期是 20 ms，1 kHz 内环每 1 ms 采一次，于是每次成功求解平均只覆盖约 1 个内环周期。

`mpc_solve()` 的到期时间是 13 项取 min，其中包含 `actuator_capability->header.valid_until_us` 与 `actuator_status->header.valid_until_us`；而执行器侧 `actuator_guard.c` 的 `header()` 把 `valid_until_us` 设为 `now + 5000`（**5 ms**）。5 ms TTL 的执行器消息决定了 MPC 快照的全部有效期。

这解释了 `outer_mpc_used = 80 / 9760`：不是 MPC 求解不出来（那是 4.1% 的另一个问题），而是**求解出来也几乎立刻过期**。

## 4.3 第 37 轮：移除执行器 TTL 的实验

把 `actuator_capability->header.valid_until_us` 与 `actuator_status->header.valid_until_us` 从 `mpc_solve()` 的 13 项到期取 min 中移除（其余不动），重建后运行 `verify_flight_entries`：

```
ENTRIES=PASS max_alt=2.098
```

与基线完全一致。也就是说，**让 MPC 快照不再被执行器 5 ms TTL 掐住，不会破坏当前 MIL 场景**。

但这一轮**没有测量参与度**（`outer_mpc_used` 需要消费侧诊断，本轮已回退），因此不能宣称"修好了 MPC 参与度低"。可确认的只有：该改法在既有验收场景下是无害的。

对照两次实验的差异值得记录：

| 实验 | 求解次数 | 快照到期链 | 飞行 |
|---|---|---|---|
| 收紧求解器容差 | 468 | 未改（被 5 ms 掐住） | **失败** |
| 移除执行器 TTL | 20 | 改（不再被掐住） | **通过** |

收紧求解器那次的失败因此不能用"MPC 被用得更多"解释——当时快照仍只活 1 ms。更可能是额外求解改变了 `m6.solver_failures` 计数、健康上报或 seed 路径。这一点需要在修好有效期之后重新验证，两个因素不能混在一起判断。

## 4.4 第 37 轮续：应用有效期修复后的原始数字

在 4.3 的基础上保留修复并记录消费侧时间戳，26 s MIL：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `life_us`（`expires - sample`） | 8,000 | **23,000** |
| `used_samples`（采用 MPC 的内环周期） | 80 | **171** |
| `solved`（求解成功数） | 20 | **9** |
| `expires_minus_eval_us`（消费时剩余） | 1,000 | **1,000** |

两点结论与一点告诫：

1. **有效期确实被拉长了**：从导航采样算起 8 ms → 23 ms，这部分修复有效、可复现；
2. **采用数翻倍但仍很低**（80 → 171 / 9760），而消费时剩余寿命仍是 1 ms，说明限制因素不只是到期链——`evaluation_time - sample_time` 本身在不同周期里很大；
3. **单点样本不可靠**：`expires_minus_eval_us` 与我先前记录的 `eval - sample`（7 ms 与 22 ms 两个不同值）都只是"最后一个被采用的样本"，不能代表分布。要下结论必须记录分布（最小值、中位数、最大值），而不是单个末值。

`solved` 从 20 降到 9 也需要解释（控制行为改变后参考轨迹不同），但同样不能凭单次运行定论。

诊断代码已回退。**下一阶段应先补"分布统计"这一课，再判断有效期修复是否足够**——否则会像本轮一样，用一个末值去推断整体。

## 4.5 第 38 轮：按 job 记录分布，两项根因分别定量

第 37 轮末的告诫是"先补分布统计，再判断"。本轮把诊断做成固件侧证据通道（`middleware/model/control/mpc_diagnostics.h`，Host 构建才落盘，不改变任何控制决策）：

- `m6_jobs.json`：每个 job 的首个拒绝阶段、solver status、primal/dual residual、独立约束违反量、推力超出量、首控制量、seed，以及 `sample/control/evaluation/expires` 四个时间戳；
- `m6_runtime_stats.json` 的 `consumer`：9760 个 1 kHz 消费点里每个备份条件的独立计数、剩余寿命直方图、MPC 与 PD 回退量的逐轴差值。

### 4.5.1 拒绝全部落在同一个阶段

488 个 job 的分布（26 s MIL，基线）：

| 指标 | 值 |
|---|---|
| 首个拒绝阶段 | `RESIDUAL` 468 个，`OK` 20 个；没有 `DOMAIN`/`REFERENCE`/`BOUNDS`/`SOLVER_CALL`/`SOLVER_STATUS`/`NON_FINITE`/`PRIMAL`/`THRUST` 拒绝 |
| solver status | 488 个 job 全部 `CONTROL_SOLVER_SOLVED`（1） |
| primal residual | min 4.7e-9，median 3.0e-8，max 1.35e-3 |
| dual residual | min 1.31e-4，p25 1.37e-3，**median 1.75e-3**，p75 3.51e-3，max 1.00e-2 |
| 独立约束违反量 | 0（p75 及以下全为 0），max 8.6e-4 |
| 推力超出量 | 0 |

结论：**失败与 QP 组装、预测模型、变量单位无关**。独立可行性检查（A·x 对原始约束、推力幅值）在所有 job 上都通过，primal 残差已达到 1e-8 量级。唯一的拒绝原因是应用侧对 dual residual 的**绝对** 1e-3 门限，而 OSQP 生成工作区里 `eps_abs = eps_rel = 1e-3`，其停止准则是 `1e-3 + 1e-3·max(‖Px‖,‖A'y‖,‖q‖)`，对本 QP 约 2e-3。实测 median 1.75e-3 正好落在 OSQP 自己的容差内：求解器按合同收敛，应用侧按更严的绝对量判负。

### 4.5.2 让求解器满足既有门限之后，飞不起来

只改求解器、**不动 1e-3 门限**（`eps_rel = 0`，按绝对 1e-3 终止）：

| 指标 | 基线 | `eps_rel = 0` |
|---|---|---|
| solved / jobs | 20 / 488 | **489 / 489** |
| max primal / dual residual | 1.35e-3 / 1.00e-2 | 9.83e-4 / 9.98e-4 |
| 被采用的 1 kHz 周期 | 80 / 9760 | **1956 / 9780** |
| 备份原因 | 9680 全部为过期 | 7824 全部为过期 |
| `limit_rejected` / `bounds_rejected` | 0 / 0 | 0 / 0 |
| **MIL 最大高度** | **2.098 m** | **0.242 m** |
| TAKEOFF（t=6.0 s）ACK | ack=1 接受 | **ack=0，reason=5（`land != LANDED`）** |

MPC 与 PD 的差值在同一轮里被逐轴记录（1956 个采用点）：x 轴 −0.330…+0.013，y 轴 −0.014…+0.326，z 轴 **−0.161…0.000** m/s²。也就是说 MPC 的水平指令与 PD 相差不超过 0.33 m/s²，**z 轴只会比 PD 更"向上"、从不更向下**。

把 0.33 m/s² 的量级放进 20% 的占空比，无法解释高度从 2.098 m 掉到 0.242 m。真正发生的是**时序**：地面保持阶段 MPC 的零偏让飞行器提前离地 0.24 m，LandDetector 不再报告 `LANDED`，于是 6.0 s 的 TAKEOFF 以 `reason=5` 被拒且不重发——验收场景再也不可能起飞。这与第 37 轮"收紧求解器 → 起飞失败"的现象一致，并且首次给出了机制，而不是"MPC 有害"的笼统说法。

> **第 39 轮更正（量级检查 → 已用实测否证）**：上段的"地面段零偏抬升"机制**不成立**。
>
> 第 39 轮在 `mpc_diagnostics.h` 增加了起飞窗口的 1 kHz 使用轨迹（`m6_use_trace.json`，记录每 tick 的 `backup`、MPC 与 PD 三轴加速度），并在两种构建上各跑一次 26 s MIL：
>
> | 构建 | 窗口 tick | 采用 MPC 的 tick（< 6.0 s） | 占空比 | z 轴 MPC−PD |
> |---|---|---|---|---|
> | 基线（`eps_rel=1e-3`） | 2040 | 8 | **0.4%** | max −0.1597 |
> | `eps_rel=0`（全解） | 2060 | 352 | **17.1%** | mean **−0.0859**，max −0.1597 |
>
> 有效平均偏置 = 0.171 × 0.0859 = **1.47e-3 m/s²**；在 1.8 s 内给出 Δv ≈ **2.6 mm/s**、Δh ≈ **2.4 mm**。
> 观测到的是 **242 mm**，相差约 100 倍。**因此"MPC 在地面段把飞行器抬起来"被直接测量否证**，不能再作为修复依据。
>
> **第 40 轮补充：也不是"提前离地导致 TAKEOFF 被拒"。** 直接打印两种构建的高度/推力时程后，`eps_rel=0` 那轮的真实形状是：
>
> | t [s] | 基线高度 [m] | 基线推力 [N] | `eps_rel=0` 高度 [m] | `eps_rel=0` 推力 [N] |
> |---|---|---|---|---|
> | 5.5 | ~0.00 | ~14.5 | 0.0105 | 14.558 |
> | 6.0 | 0.0000 | 14.541 | 0.0037 | 14.800 |
> | 8.0 | **1.2887** | 14.197 | **0.1176** | 14.704 |
> | 10.0 | ~2.09 | ~14.2 | 0.2270 | 14.563 |
>
> 也就是说：6.0 s 时飞行器**仍在地面**（3.7 mm），不是被提前抬起；之后它确实在爬，但**爬升率约为基线的十分之一**，而推力并不更低（8.0 s 时 14.704 N > 基线的 14.197 N）。"推力更高、爬升更慢"这个签名与"指令不够大"矛盾，更像竖直通道的**有效方向/参考**不同（例如姿态倾斜把推力分到水平、或竖直速度/高度参考在两种构建下不同）。
>
> 结论只到事实层：**mpc 全解并不改变地面段离地（否证），也不会让 TAKEOFF 因离地而被拒（否证）；它让爬升率掉一个量级，而推力反而略高。** 机制仍未定位。下一项判别测量：在两种构建上按 20 ms 记录 `backup`、`control_level`、guidance `state/mode`、参考竖直加速度、姿态倾角与竖直速度，覆盖 5.5–9 s。在该测量完成前不得再提出修复方案，也不得据此要求用户做控制层决策。
>
> **第 41 轮：把轨迹窗口扩到 10.5 s 后，位置环指令被排除。** 同一 `eps_rel=0` 构建，按 1 kHz 分窗口统计（NED 系，+z 向下）：
>
> | 窗口 | 采用占空比 | PD 的 z 指令均值 | MPC 的 z 指令均值 | MPC−PD |
> |---|---|---|---|---|
> | 4.0–6.0 s（地面） | 20.0% | +0.1941 | +0.1080 | −0.160 … −0.001 |
> | 6.0–8.0 s（爬升） | 20.0% | +0.2415 | +0.1302 | **−0.161 … −0.059** |
> | 8.0–10.5 s（爬升） | 20.0% | +0.3512 | +0.2003 | **−0.161 … −0.119** |
>
> 在爬升段，MPC 的 z 指令**比 PD 更向上**（少向下 0.06–0.16 m/s²）。如果位置环指令是原因，采用 MPC 应该让爬升**更快**，而实测是慢 10 倍。**因此位置环加速度指令被排除为原因**；剩下的差异必须在位置环之外（姿态/推力方向、竖直速度或高度参考、land 证据链）。
>
> 这也意味着：即使把 MPC 的代价权重或门限调到"完全正确"，只要"接受解"这一步本身改变了别的东西（例如 `backup=0` 导致 `control_level`/`health_state` 变化，或求解耗时改变了任务相位），爬升仍会失败。**修复的入口不在 MPC 的数学里**，这一点必须在动任何控制参数之前确认。
>
> **第 42 轮：把"未知通路"缩小到一个 4 条件谓词。** 逐条排除后剩下的候选只有 land 判定链：
>
> - `control_level` 在 `controller.c:590` 被写入，但**全仓库没有任何读取点**（`middleware/` 仅此一处）——排除；
> - `health_state` 只被 FMS 的 prearm 第 10 项与 operator authority 读取，而 MIL 里 prearm 由 `verified_input_mask` 位 10 兜底通过——不作为首选；
> - TAKEOFF 的 `reason=5` 来源已定位到 `fms.c:648`：`e->land.state != LANDED_STATE_LANDED`；
> - `e->land.state` 由 `fms_safety.c:86-119` 决定，`LANDED` 需要 `ground_contact == CONTACT` **且** `ground_stable`，而 `ground_stable` 是四个数值条件的合取（`fms_safety.c:101-104`）：
>
>   | 条件 | 阈值 |
>   |---|---|
>   | 水平速度 `hypotf(v0,v1)` | ≤ **0.20 m/s** |
>   | 竖直速度 `|vz|` | ≤ **0.15 m/s** |
>   | 竖直加速度 `|a_z|`（`fms_motion_acceleration`） | ≤ **0.50 m/s²** |
>   | 导航能力掩码与 `NAV_VALID_ACCELERATION` 等位 | 必须齐全 |
>
> 并且 LANDED 还必须保持 `landed_dwell_us`（2 s）。因此"MPC 是否让这四个条件之一失效"是一个可判定问题，而不是猜测。

> |---|---|---|---|---|
> | 基线 | **0.0029 m/s** | 从未 | 0.0611 | 2.0982 m |
> | `eps_rel=0` | **0.5802 m/s** | **t = 5.237 s 起越过** | 0.0430 | 0.2420 m |
>
> 同时测得地面上 MPC 与 PD 的**水平**指令差：x 轴 MPC 比 PD 平均少 **0.2038 m/s²**（PD 均值 +0.7687，MPC 均值 +0.5558），采用占空比 20%。
>
> 由此得到一条**两环已实测、第三环未实测**的链条：
>
> 1. ✅ MPC 被采用时水平指令比 PD 少约 0.20 m/s²（20% 占空 ⇒ 净差约 0.04 m/s²）；
> 2. ✅ 该净差在地面把飞行器推向 **0.58 m/s**，而基线只有 0.0029 m/s；Plant 第一版**无水平地面摩擦**（P-17），所以水平速度不会被耗散，只会累积；
> 3. ❓ 该速度越过 `fms_safety.c:101-104` 的 `|v_h| ≤ 0.20` 之后，`land.state` 是否真的退回 UNKNOWN 并导致 `fms.c:648` 的 `reason=5`。
>
> 第 3 环**没有**被证实：Host SIL 状态帧第 78 列在两种构建的地面窗口里都是 0，说明它不是实时 `land.state`（或该列语义与假设不同），因此不能用它下结论。**要确认第 3 环，必须在 FMS 内部记录 `land.state`/`stable_ms`**，这是下一轮唯一需要写的代码。
>
> **第 44 轮更正：`reason=5` 本身是二义的，第 3 环连"哪个判据失败"都还没确定。** 读 `fms.c:647-648` 原文：
>
> ```c
> if (!fms_capable_for_mode(e, in, FLIGHT_MODE_POS_HOLD, 1u) ||
>     e->land.state != LANDED_STATE_LANDED) { r.reason_code = 5u; break; }
> ```
>
> `reason=5` 既可能是 **land 状态**失败，也可能是 **`fms_capable_for_mode`** 失败（导航能力掩码不足以支撑 POS_HOLD）。因此第 43 轮链条的第 3 环不仅要验证"land 是否退回 UNKNOWN"，还要先排除"能力掩码不足"这一支。判别材料现成：`mil_diagnostics.json` 已记录每条命令 ACK 时刻的 `maximum_navigation_mask`、prearm 状态与 failed mask——**下一次跑 `eps_rel=0` 构建时读这份文件即可分流**，不需要新增固件代码。
>
> 这也再次说明"两环实测"不足以定根因：同一行代码有两个成因，选错分支会导出完全错误的修复方向。
>
> **第 45 轮：已分流——是 land 分支，不是能力分支。** 用状态帧直接读导航能力掩码（第 12 列），两种构建在 6.0 s 前后都是 **0xFF**（POS_HOLD 只需 0x78），且 prearm 恒为 2（READY）、failed mask 恒 0。因此 `fms_capable_for_mode` **不成立为失败原因**，`reason=5` 只能来自 `land.state != LANDED` 这一支。
>
> 至此链条的四环状态：
>
> | 环节 | 状态 | 证据 |
> |---|---|---|
> | MPC 在地面的水平指令比 PD 少 0.2038 m/s² | ✅ 实测 | `m6_use_trace.json`，占空 20% |
> | 地面水平速度被推到 0.58 m/s（基线 0.0029） | ✅ 实测 | Plant 状态，越过 0.20 门限于 t=5.237 s |
> | `reason=5` 来自 land 分支而非能力分支 | ✅ 已分流 | nav mask 0xFF、prearm READY、failed 0x00 |
> | `land.state` 实际在何时退回非 LANDED | ❌ 仍不可观测 | 状态帧第 78 列在两种构建里都是 0，**不是**实时 land state |
>
> 唯一剩余的不可观测项是"land 状态本身的时序"。它不影响修复方向的选择——因为第 2 环已实测越过 `ground_stable` 的 `|v_h| ≤ 0.20` 门限，而 `ground_stable` 是 LANDED 的必要条件（`fms_safety.c:107-110`）。**可以下的结论**：MPC 的接受解在地面造成水平速度不平衡，使 LANDED 无法成立，从而 TAKEOFF 被拒、场景无法起飞；竖直通道、导航能力、prearm 均已排除。
>
> **需要用户决策的修复选项**（三者都需要控制层判断，不能由 Agent 自选）：
>
> 1. 地面段不给水平加速度授权（LANDED 期间零水平指令）；
> 2. 地面段不采用 MPC 快照（保留 PD 的位置保持）；
> 3. 给 Plant 地面加水平摩擦（改物理模型，影响 P-17 的既有结论）。
>
> **第 47 轮：可实施性核对后，推荐顺序要改。** 检索 `middleware/model/control/` 全目录，**只有一个命中，而且是我自己加的注释**——控制模块**完全没有 landed/ground 概念**，`ControllerInput` 里没有任何离地信号。由此：
>
> | 选项 | 是否需要新的契约输入 | 实际成本 |
> |---|---|---|
> | 1 地面段零水平授权 | **需要**（控制器必须先知道自己在不在天上） | 契约字段 + 输入校验 + FMS 发布 + 两端主机测试，属跨模块改动 |
> | 2 地面段不用 MPC | **需要**（同一个原因） | 同上，且会牺牲空中段覆盖率（正是待修指标） |
> | 3 给地面加水平摩擦 | **不需要**（纯物理） | 只改 Plant 模型，但会推翻 P-17"第一版无水平摩擦"的既有结论，需要同步改 P-17/P-15 判据与文档 |
>
> 所以我上一轮"推荐选项 1"是不成立的——它看起来最小，实际要动契约。**在"改动范围"这个维度上，最省的是选项 3**；但它是唯一会改变已验证物理语义的选项。这不是 Agent 该替用户做的取舍：选 1/2 意味着接受一次契约扩展，选 3 意味着接受一次物理模型修订。
>
> 补一条可选路径供参考：也可以**不改任何一侧**，而是在验收场景里让 TAKEOFF 的 LANDED 判据不依赖水平速度（例如地面段改用 ground_contact 为主的证据）。但那等于改验收标准，**本 Agent 不提议、也不实施**。
>
> 顺带记录一个尚未解释的现象：**基线能起飞，但状态帧里的 land 列同样恒为 0**——说明该列不是 land state，或者是另一个只在特定时刻更新的信号。这一点在改动 land 相关逻辑前应当先核清。
>
> **第 46 轮：该现象已解释，不是缺陷。** `spec/MATLAB-验收与结果提交.md` 第 4 节明确规定：状态帧**第 75～108 列只在首次进入 `FAILSAFE_TERMINAL` 时锁存一份快照**，其中包含 LandedState。两种构建在地面窗口都没有进入终端 failsafe，所以第 78 列恒为 0 是**规定行为**，而不是 land 状态没更新。
>
> 这带来两个必须记住的操作结论：
>
> 1. **不得**用第 78 列判断实时 land 状态——它是终端快照，只有发生终端 failsafe 才有意义（我在第 43–45 轮两次误用，已在此更正）；
> 2. 若要观测实时 land 状态，只能走 FMS 输出（`fms_output.landed_state`，含 `state`/`evidence_mask`/`confidence`/`stable_duration_ms`）或新增专用诊断列，**不要**复用 75～108 的终端快照区。
>
> 当前状态：链条的解释力很强（两个构建在"是否滑移"上有 200 倍差异，且阈值被精确越过），但按前三轮的教训，**在两环实测、一环未实测时不宣称根因**。可确定的是：**失败与 MPC 的竖直通道无关，与"接受解在地面产生水平速度不平衡"有关**；修复候选（地面段不给水平加速度授权 / 地面段不使用 MPC / 给地面加摩擦）都必须等第 3 环确认后再选，且属控制层决策。

本轮实验已整条回退（`eps_rel` 恢复 1e-3，MIL 回到 2.098 m / TAKEOFF ack=1），只保留诊断通道。

### 4.5.3 快照寿命的分布（不再是末值）

基线 20 个成功 job 的 `expires - sample` 恒为 **8000 µs**，`expires - evaluation` 恒为 **5000 µs**；`evaluation - sample` 恒为 **3000 µs**。5000 µs 恰好等于 `actuator_guard.c` 的 `valid_until_us = now + 5000`，与 §4.2 的判断一致，并且这次是每个 job 的完整分布，不是最后一个样本。

### 4.5.4 下一阶段的入口

按依赖顺序：

1. **地面段与空中段分离**：MPC 的零偏在 `LANDED` 期间必须不改变离地判定（例如地面段不采用 MPC 快照，或采用但把净加速度限幅到不产生升力），否则任何提高接受率的修复都会以 `reason=5` 失败。这是"接受率"与"起飞前置条件"的耦合，不能用调容差绕过。
2. **快照到期链**：把 `actuator_capability/status` 的 5 ms 消息 TTL 从计划有效期里移除。计划不是执行器遥测的函数——这两项根本不进入 QP——5 ms 是消息新鲜度契约，不是计划有效期。§4.3 已证明该改动在既有场景下无害。
3. **门限与求解器的一致性**：1e-3 门限保留，把 OSQP 的终止准则改成绝对（`eps_rel = 0`，或重新生成工作区）。第 1 项完成前不得单独启用。

## 4.6 第 48 轮：两项修复后接受率 100%，地面滑移随之消失（附第 43–45 轮机制的更正）

第 43–45 轮把失败归因为"MPC 的地面水平指令比 PD 少 0.2038 m/s²，把飞行器推到 0.58 m/s"。本轮用同一套只读诊断（1 kHz 消费轨迹 + 2 kHz Plant 状态与电机力）重做三个构建，**该归因不成立**：

| 构建 | 唯一改动 | solved/jobs | 消费点 used/samples | 快照寿命 | 地面 `|v_h|` max | 地面俯仰范围 | MIL 最高 |
|---|---|---|---|---|---|---|---|
| 基线 | 无 | 20/488 | 80/9760（0.8%） | 8 ms | 0.0026 m/s | −0.038…+0.005° | 2.0982 m |
| `eps_rel=0` | 求解器绝对终止 | **489/489** | 1956/9780（20.0%） | 8 ms | **0.5802 m/s** | **−1.032…+5.347°** | 0.2420 m，TAKEOFF `reason=5` |
| `eps_rel=0` + 到期链 | 再把执行器 TTL 移出计划有效期 | **488/488** | **9272/9760（95.0%）** | 0–19 ms | 0.0459 m/s | −0.463…0.000° | **2.0841 m**，TAKEOFF 通过 |

三项与旧结论冲突的实测：

1. **滑移方向上位置环在"刹车"，不是在"推"**。`eps_rel=0` 构建在地面时 PD 与 MPC 的 x 指令都是正值（5.4 s：PD +1.026、MPC +0.799 m/s²），而飞行器实际沿 −x 漂移（5.9 s 位置 −0.3285 m、速度 −0.575 m/s）。所谓"MPC 比 PD 少 0.2 m/s²"的方向与运动方向相反，因此不可能是推力源。
2. **水平加速度 100% 由推力倾角解释**。用 Plant 四元数取机体 z 轴 `b3`，`a_thrust = -ΣT·b3/m` 与实测 `a` 在每一采样点吻合，最大残差 **0.040 m/s²**（基线 0.0004，修复构建 0.0031）。也就是说地面既没有水平摩擦，也没有隐藏的侧向接触力（与 P-17 一致），滑移只可能来自倾斜的推力矢量。
3. **倾斜方向与指令相反**。地面窗口内期望俯仰（由施加的加速度指令反算）为 −0.6°…−11.0°（低头），实测俯仰为 +0.04°…+5.35°（抬头）。

机制（与测量一致，但"激励源"只做到如下程度）：计划寿命只有 8 ms 而外环周期是 20 ms，于是 1 kHz 消费点在 MPC 与 PD 之间**每 20 ms 切换若干次**（`m6_use_trace.json`：`backup` 标志在 1–4 tick 的 MPC 段与 16–19 tick 的 PD 段之间反复）。两种指令的差值约 0.1–0.15 m/s²（0.6–0.9°），每次切换都是一次阶跃；`controller.c` 的期望角速度前馈用 `-delta/dt` 对期望姿态做一阶差分（`dt=1 ms`），0.6° 的阶跃即 10 rad/s，被 `max_body_rate` 截到 2 rad/s。地面段该激励把机体推到 5.3° 抬头，离地判定随 `|v_h|` 越过 0.20 m/s 失效。

**本轮只改变一个变量就消除了它**：把执行器 TTL 移出到期链后，快照寿命 19 ms，消费占空比 0.8% → 95%，切换消失，俯仰峰值 5.35° → 0.46°，`|v_h|` 0.58 → 0.046 m/s，MIL 恢复到 2.0841 m 且 TAKEOFF 通过。因此**修复入口是计划寿命/消费连续性，不是 MPC 的数学，也不需要 landed 契约输入**；第 47 轮"三选一都需要控制层决策"的结论同样被这条证据取代。

仍未隔离的一项：`-delta/dt` 前馈在切换阶跃下的实际贡献没有单独做对照实验（要隔离它需要只改前馈、保留 8 ms 寿命的构建）。上表的因果关系只到"寿命/占空比"这一层；若后续要动前馈，必须先做这个对照。

修复（Flight `test/fmat-0012-m6-controller` @ `b2f33ee`）：

- `mpc.c`：`actuator_capability/status` 的 5 ms TTL 不再参与计划有效期（两者都不进入 QP）；
- `mpc.c`：`mpc_reset()` 通过 `osqp_update_settings()` 把工作区改为绝对终止（`eps_rel = 0`、`eps_abs` 仍为 1e-3），使求解器满足应用侧**未改动**的绝对 1e-3 残差门限（实测 max `dual_res` 999e-6）。生成的工作区文件与 `UPSTREAM_LOCK.json` 保持逐字节一致，因此依赖锁无需变动。

### 4.6.1 覆盖率分母：现有门限在数学上不可达

同一轮运行的原生计数：

| 项 | 值 |
|---|---|
| worker tick（50 Hz × 26 s） | 1300 |
| `blocked_mode`（模式不是 trajectory） | 549 |
| `blocked_validation` | 263 |
| 真正求解的 job | 488 |
| 每次成功记入的覆盖时长 | 20 ms |
| 整轮分母 | 26 s |

按 `covered_us / 整轮时长`，即使**每一个** worker tick 都求解成功，上限也只有 `751 × 20 ms / 26 s = 57.8%`，因为 549 个 tick 在非 trajectory 模式下根本不进入 `mpc_solve()`。当前实现已达到它的上限结构之内的最好结果（488/488 全解），但 `m6_report.json` 的 `coverage_90` 仍然是 FAIL。

三个可选口径（本轮只测量，不切换）：

| 口径 | 本轮值 | 上限 | 说明 |
|---|---|---|---|
| 整轮 26 s（当前实现） | 37.5% | **57.8%（结构上限）** | 与"闭环时长"不等价：被 disarm/着陆段稀释 |
| worker 可用窗口 15.02 s | 65.0% | 100% | 仍受 263 个 `blocked_validation` 影响 |
| 1 kHz 消费点 `used/samples` | **95.0%** | 100% | 唯一直接测量"控制路径上 MPC 实际接管了多少时间" |

`fallback_counted_as_uncovered` 在任何口径下都成立（PD 回退时长计入分母），所以切换到消费点口径不是放宽门限，而是把分母改回它本来的含义。**这是验收标准变更，需用户裁定后由 Issue #12 记录**；在裁定前 `verify_m6_jobs.m` 的判定口径保持不变。

## 5. 边界

本节确认了消费路径、拒绝阶段分布、地面滑移的真实来源（计划寿命导致的 MPC/PD 快速切换），并提交了 §4.6 的两项修复；**没有**放宽 1e-3 门限、没有跳过候选解验证、没有延长旧解有效期、没有改 Plant 物理，也没有为提升指标修改 `run_component_checks` 的判定。第 37、38、39 轮的三次实验（含 `eps_rel=0` 单独启用）仍全部回退；当前 Flight 工作树只包含诊断通道与 §4.6 的两项修复。
